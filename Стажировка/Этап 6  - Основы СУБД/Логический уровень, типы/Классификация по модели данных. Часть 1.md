ффОдно из важных мест взаимодействия пользователей с компьютером занимают языки запросов, используемые для извлечения информации из БД. Качество выполнения запросов пользователей зависит от структуры представления данных (модели данных), рассматриваемой предметной области.

В теории БД понятие модель данных является одним из фундаментальных.

**Модель** – широкое понятие, включающее в себя множество способов представления изучаемой информации.

**Модель данных** – это совокупность функциональных характеристик объектов и особенностей представления информации. Модель данных – это совокупность, трёх составляющих:
1) набора типов данных (являющихся блоками при построении БД);
2) набора операторов или правил вывода, предназначенных чтобы находить, выдавать или преобразовывать информацию, содержащуюся в любых частях структуры;
3) набор правил целостности, которые определяют множество непротиворечивых состояний базы данных.

Основные уровни абстрагирования в БД: информационный; внешний; концептуальный; внутренний. На каждом уровне абстрагирования используются разные модели данных. Классификация моделей представлена
![477](../../images/Архитектура%20и%20модели%20данных-28.03.2026-15_03.png)

**Инфологическая (концептуальная) модель (ИЛМ)** должна отображать информацию о предметной области (ПО) и смысл взаимосвязи объектов ПО в виде, независимом от конкретной используемой СУБД.
На этом уровне поддерживается представление БД для конечных пользователей, а описание БД осуществляется на естественном языке в терминах предметной области, которыми оперируют конечные пользователи.

**Модель «сущность-связь»** представляет собой совокупность понятий и графических символов для построения инфологических моделей. Модель была предложена Питером Ченом в 1975 году и стала стандартом инфологического моделирования.

**Даталогические (логические) модели (ДЛМ)** могут поддерживаться конкретными СУБД.
**Документальные модели** соответствуют представлению о слабоструктурированной информации обычных текстовых и гипертекстовых документов, словарей, классификаторов.
**Фактографические модели** структурированы, например, в популярной реляционной модели данные структурированы в виде отношений. Отношение представляет собой двумерную таблицу, каждая ячейка которой должна содержать одиночное значение.
**Реляционные отношения** мало пригодны для хранения объектов, используемых в объектно - ориентированном программировании. Объекты могут содержать сложные структуры данных, указатели на другие объекты. Кроме того, у объектов есть исполняемые функции – методы, которые также необходимо хранить. Множество объектов с одним и тем же набором свойств и методов образуют класс объектов.
Для постоянного хранения объектов разработаны специализированные объектно-ориентированные СУБД (ООСУБД). **ООСУБД** позволяют хранить данные экземпляров объектов и методы класса объектов. Объектно-реляционные СУБД сочетают реляционный и объектный подходы к хранению объектов. Существуют и другие модели, такие как постреляционная, многомерная, семантическая и т.д.
**Физические модели** создаются на внутреннем уровне и характеризуют организацию внешней памяти и структур хранения. Это внутренняя модель ФБД.
## Иерархическая модель данных
**Иерархическая модель (ИМД**) представляет собой связный граф в виде дерева.
![](../../images/Архитектура%20и%20модели%20данных-28.03.2026-15_03-1.png)

Достоинство ИМД – простота и естественность отображения взаимосвязи между объектами.
Недостатки ИМД:
– устанавливает порядок доступа к данным и требует от пользователя знания путей доступа к данным по ветвям дерева при разработке процедур обработки данных.
– позволяет моделировать только связи типа «1:1», «1:М», «М:1».

## Сетевая модель данных
**Сетевая модель (СМД)** является более общей структурой, по сравнению с ИМД. В сетевой модели любой элемент может быть связан с любым элементом, любой узел может быть как исходным, так и порожденным, любой узел может иметь произвольное количество исходных и порожденных узлов.

Сетевой подход позволяет моделировать связи типа «1:1», «1:М», «М:1», а также связь типа «М:N».
**Пример сетевой структуры** (рис. 2.4) - структура для представления информации об изделиях, деталях и составе изделий, так как каждое изделие может содержать разные детали, а каждая деталь может входить в состав разных изделий:

![](../../images/Архитектура%20и%20модели%20данных-28.03.2026-15_03-2.png)Рис. 2.4. Пример сетевой структуры

Достоинства СМД - позволяет моделировать отношения типа «М:N», часто встречающиеся в ПО.
Основной недостаток СМД – структуры для представления данных значительно сложнее, чем в других моделях.
![](../../images/Архитектура%20и%20модели%20данных-28.03.2026-17_03.png)
Элемент данных — это наименьшая поименованная информационная единица данных, доступная пользователю (аналог — поле в файловой системе). Элемент данных должен иметь свой тип (не структурный, простой).
Агрегат данных соответствует следующему уровню обобщения — поименованная совокупность элементов данных внутри записи или другого агрегата
Запись — конечный уровень агрегации. Каждая запись представляет собой именованную структуру, содержащую один или более именованных элементов данных, каждый из которых обладает своим особым форматом.
Набор — это поименованная двухуровневая иерархическая структура, которая содержит запись владельца и записи членов. Наборы выражают связи "один ко многим" или "один к одному" между двумя типами записей. Тип набора поддерживает работу с внутренними структурами типов записей.
База данных в сетевой модели данных — это поименованная совокупность экземпляров записей различного типа и экземпляров наборов, содержащих связи между ними.

## Реляционная модель данных
Основной структурой данных в реляционной модели (РМД) является отношение, поэтому модель получила название реляционная. В РМД данные организованы в таблицы, которые должны удовлетворять определенным ограничениям, и могут рассматриваться как отношения.
**Достоинства реляционной модели:**
–     простота и наглядность модели;
–     однородность структур для представления объектов и связей (в виде отношений); Единообразие представления данных в РМД упрощает программные и языковые средства СУБД.
–     наличие стандартизованного высокоуровневого языка запросов к БД, позволяющего манипулировать данными без необходимости знания конкретной физической организации БД во внешней памяти;
–     наличие специальных средств ускоренного доступа к информации (индексы, хэширование);
–     возможность приведения других моделей к реляционной модели.

| **Неформальный термин**                                      | **Формальный реляционный**<br>**термин**  |
| ------------------------------------------------------------ | ----------------------------------------- |
| Таблица                                                      | Отношение                                 |
| Строка, запись                                               | Кортеж отношения                          |
| Количество строк                                             | Мощность отношения,<br>кардинальное число |
| Столбец, поле                                                | Атрибут отношения                         |
| Количество столбцов                                          | Степень, арность отношения                |
| Уникальный идентификатор строки                              | Первичный ключ отношения                  |
| Общая совокупность допустимых<br>значений некоторого столбца | Домен                                     |
| Строка заголовков столбцов таблицы                           | Схема отношения                           |

**Ограничения реляционной модели - свойства таблиц:**
1.   Каждая таблица уникально именована, представляет один реальный объект или определяет связь между объектами и состоит из однотипных строк, соответствующих кортежам отношения, и столбцов, соответствующих атрибутам отношения.
2.   Каждый элемент таблицы должен быть атомарным, т.е. неделимым.
3.   Все строки имеют одну и ту же структуру с фиксированным числом полей и значений. В таблице не может быть двух одинаковых строк. Строки отличаются друг от друга хотя бы одним значением.
4.   Каждый столбец уникально именован. Элементы одного столбца должны быть однородными, извлечены из одного домена.
5.   В операциях с таблицами строки и столбцы могут просматриваться в любой последовательности. Упорядоченность кортежей отсутствует, а домены упорядочены внутри отношения. Но порядок обращения к именованным столбцам также становится несущественным.
6.   Каждая таблица должна иметь первичный ключ. Ключ позволяет найти единственную строку в таблице.
